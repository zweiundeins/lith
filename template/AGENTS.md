# app: notes for coding agents

app is a Go, SQLite and Datastar application on lith (github.com/zweiundeins/lith), started from lith's template. Read the lith skill before changing code. Its rules shape every change here (one writer, commands that touch topics, views rendered once per tick for all tabs, outcomes on the stream, tab state in SQLite), and its references hold the recipes, the review checklist and the Datastar gotchas. The skill ships with lith, so it matches the lith version in go.mod:

    $(go list -m -f '{{.Dir}}' github.com/zweiundeins/lith)/skills/lith/SKILL.md

## Layout

- `cmd/app`: the binary (`serve`, `backup`, `--version`) and its wiring: database, writer, render loop, the edge, shutdown, the hourly sweep. `/static/` is mounted outside `edge.Sessions`, so its public, immutable answers carry no cookie. A stream counts under its client's address (`live.Spec.Client`), at most `-client-streams` (16) of them, so one address cannot hold every stream under `-streams`. An action for a tab whose stream is not open gets 409 (`live.Hub.HasStream`) and writes no row. Every flag can also come from the environment (`-db` as `APP_DB`). `metrics.go` serves the metrics for Prometheus on a loopback listener of their own, never the public one: `lith/prom` and `lith/dbmetrics/prom` under the namespace `app_`, the Go runtime and the process. `-metrics` sets the address: `auto` (the default) is 127.0.0.1 at `-addr`'s port + 100, `off` is none. `TestDashboard` checks the names against the dashboard and alert rules in lith's `deploy/observability`.
- `internal/guestbook`: the template's example feature. Commands (`Sign`, `Sweep`) in `commands.go`, queries in `queries.go`. Replace it with the first real feature. A status code carries nothing a person reads: what the person caused (a name too long, the newest entry again) is a refusal that `Sign` records in the tab's row, answered 204; what no command decided (a rate limit, a failed write) is a notice on the tab's stream (`live.Hub.Notify`, in `web.notify`), and a deploy ends every stream with one (`live.Options.Stopping`, `web.Stopping`); both carry the op id that ends the page's pending state. The pending state ends on a signal, never on a clock: the op's ack on the stream, Datastar's `retries-failed`, an answer of 400, which comes without a notice, or the stream connecting again (`openStream`, `retrying`, a tab that shows after it hid) with a tab row that does not ack the op, once no request of its key is in flight; a 409 (the tab had no stream) waits for that reconnect like a 5xx. In the last three the page speaks in its own words and keeps what was typed. The ops live in `$_ops` by key (the form's is `sign`), and their requests go out from elements of their own in the hidden `#ops`, whose listeners (`fetched`, `patched` in `expr.go`) no frame removes: add a form's or a button's op with `act(key, path, payload)`, a `$_ops` entry and the key in the tab's row. A command that runs long records its acceptance in the tab's row first, so its op is acked at once.
- After a deploy every tab's stream reconnects and its views render afresh, but the rest of the page is the old process's HTML. The page reports its build (`$_build`, from `live.Hub.Build`, which `cmd/app` sets to `buildVersion()`), its assets version (`$_assets`) and whether the person typed (`$_dirty`) as signals in its stream request, which `web.stream` reads with `sse.ReadSignals`, and its path in a header; never report one that changes in a header, since Datastar repeats a `@get`'s first headers when it reopens the stream after a retry or a hidden tab, and `web.refresh` (`live.Spec.Refresh`) answers a page of a former build: `#content` rendered afresh, or, when the person typed or the assets changed, a notice in `#update` that asks for a reload. lith then patches `$_build`, so the next reconnect costs nothing. The stream's element, `#ops` and the signals stay outside `#content`: a morph of the stream's element would open a second stream, and lith skips such a refresh.
- `internal/views`: templ components, and the Datastar expressions they use (`expr.go`).
- `internal/web`: routes, handlers, the live views, static files. `static/vendor` holds Starbase's patched Datastar build; its `VERSION` says which. lith's `newest-frame.js` (`live.NewestFrame`, vendored from github.com/mbolli/datastar-attribute-newest-frame) is served beside them as `/static/lith/newest-frame.<hash>.js`, and the page loads it after Datastar, with `data-newest-frame` on its body. It applies the newest frame of each view, and when the page falls behind its stream, it dispatches `newest-frame-behind`, which `<body>` posts to `POST /pace` (`pace.go`). The handler counts the report with `live.Hub.Behind` (`app_live_newest_frame_behind_total`) and paces that stream with `live.Hub.Pace`: the hub then sends the page a write only once it has acknowledged the last. The stream's `live.Spec.Ack` ends each paced write with an element that posts `POST /ack` after the paint, with the page's round trip, and the hub sends every frame again once the page keeps up for 5 s. Streams are named after the session and the tab (`streamID`), so `/ack` and `/pace` reach only the request's own streams; both are limited per client address first (`edge.ClientKey`: a session id is no limiter key, since a client mints a new one with every request that sends no cookie), then `/pace` per session and `/ack` per stream. A page that keeps up never posts either. Paced, a slow phone gets a third of the bytes; on a far link it gets one frame per round trip, so it lags a little more than with the plugin alone (lith's streams guide has the numbers). Without `Ack` in the stream's `Spec`, `/pace` only counts. Scripts and stylesheets go out minified (`edge.Minify(minify.Bytes)`, from `github.com/zweiundeins/lith/minify`), and as written with `-dev`.
- `migrations`: `NNN_name.sql`, applied in order at startup. Add a file for every schema change, never edit one that has shipped.
- `deploy`: systemd units, the Caddy site block, deploy script, backups, and in `deploy/observability` the metrics target, the probes and the log shipping a host's Prometheus and Alloy load (`deploy/README.md`). The metrics port, 8180, is in three places: the unit's `-metrics` and `SocketBindAllow`, and `app.metrics.yml` (`TestMetricsPort`).
- `benchmarks/RESULTS.md`: measured numbers, each with its date, machine and command.

## Commands

- `go tool task dev`: serve on http://127.0.0.1:8080 with `-dev`, static files as written, and rebuild on every change. The metrics stay on, at http://127.0.0.1:8180/metrics.
- `go tool task test`: vet, gofmt, `go test -race ./...`.
- `go tool task build`: the static binary.
- `go tool templ generate` after editing a `.templ` file. The `_templ.go` files are committed.
